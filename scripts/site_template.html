Abstract

Coding agents fail on most real GitHub issues, and the verdict usually comes only at the end of a run. We read an agent's run step by step, like an ECG reads a heartbeat, and ask after every step whether the run will resolve its issue. We contribute a TimeNet dataset of $n_ckpt checkpoints from $n_runs SWE-agent runs, where each checkpoint holds the first $k_first to $k_last steps of a run that is still going: 19 per-step series, the agent's thoughts and the issue text. We fine-tune three OpenTSLM models on different inputs and compare each with a CPU baseline that reads exactly the same inputs, on $test_runs runs from $test_repos repositories never seen in training. The behaviour signal grows over the run, and the best TSLM comes within $gap_lo–$gap_hi AUROC of the best CPU model, though every TSLM stays below its CPU counterpart. Replayed as a live monitor on $mon_total unseen runs, TSLM A's alarms are right $a_right of the time and fire at a median step of $a_median.

The Agent ECG

Our TimeNet connector for nebius/SWE-agent-trajectories (TimeNet PR #832) cuts every run into checkpoints: the first $k_first, 10, 15, 20 or $k_last steps of a run that is still going. A checkpoint never contains the end of the run, so no input gives the outcome away. The "ECG" is 19 series with one value per step. It is a multichannel event trace, not a waveform:

4 lengths

the agent's thought, its command, the environment's reply, and the whole conversation so far

5 actions

edit, create a file, run code, read, search

5 replies

rejected edit, traceback, command error, timeout, silent success

5 patterns

repeated command, same file as the last edit, and whether an edit touches a source, test or own file

The data is split by repository, so no repository or issue appears in two splits. Most runs fail, and the longer a run goes on, the more likely it is to fail:

As a Live Monitor

A monitor turns each prediction into a health score from 0 to 100 and sounds the alarm after $hold critical steps in a row. We replayed $mon_total unseen test runs step by step through two monitors: TSLM A, and the CPU model of the signals. The runs were all $mon_resolved resolved test runs with at least 20 steps, plus $mon_failing random failing ones; neither monitor chose them.

A's Other Two Tasks

Besides pass or fail, TSLM A learns to predict how a run will end (one of six endings) and to write a short status report whose last sentence forecasts the rest of the run. Scores on $task_scope, pooled over checkpoints:

$task_rows
ModelEnding accuracyEnding macro-F1Report format followedRemaining steps, mean (median) errorPass/fail balanced accuracy

The majority baseline always predicts the most common ending, the median remaining steps, and "will not resolve".

A is about level with the CPU signals model on the ending and writes reports in the right format almost every time. Its forecast is weaker: its remaining-steps error and its pass/fail call in the report both trail the CPU signals model.

Limitations

  • The TSLMs do not beat simple models. Gradient-boosted trees and logistic regression on a laptop CPU score higher than every TSLM with the same inputs.
  • Combining them adds nothing. Averaging TSLM A with the best CPU model, without fitting anything on test, gives no gain: every interval is around zero.
  • We do not yet know how much A relies on the ECG. The test that shuffles A's series between runs has not been run. C reads the ECG alone and is above chance; for A, part of the signal is how hard the issue is.
  • The test split is small at late checkpoints. Differences under about 0.05 AUROC on a single split are not reliable; the intervals in the chart show how wide they are.

Training

All three models are OpenTSLM-SP on $llm, fine-tuned from $base on one $gpu each. C reads the ECG only, B reads the agent's thoughts and the ECG, and A reads the issue, the thoughts and the ECG and learns three tasks: pass or fail, how the run will end, and a short status report. Training took $h_c h (C), $h_b h (B) and $h_a h (A), $gpu_hours GPU-hours in all. OpenTSLM's eager attention ran out of memory on A's long prompts; switching to PyTorch SDPA (the same math) made A fit and cut its training time by more than half.
