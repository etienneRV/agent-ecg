Agent ECG: Warning Early When a Coding Agent Is Going to Fail

Barış Gürel, Maximilian Lohscheller, Ziyad Mellal, Etienne Ritter Vidal

TimeNet Hackathon, Round 1 · 2026

Code Dataset TimeNet connector OpenTSLM

Abstract

Coding agents fail on most real GitHub issues, and the verdict usually comes only at the end of a run. We read an agent's run step by step, like an ECG reads a heartbeat, and ask after every step whether the run will resolve its issue. We contribute a TimeNet dataset of $n_ckpt checkpoints from $n_runs SWE-agent runs, where each checkpoint holds the first $k_first to $k_last steps of a run that is still going: 19 per-step series, the agent's thoughts and the issue text. We fine-tune three time-series language models (TSLMs), language models that read time series alongside text, built with OpenTSLM on Llama 3.2 1B. Each reads different inputs and is compared with a classical baseline that reads exactly the same inputs, on $test_runs runs from $test_repos repositories never seen in training. The behaviour signal grows over the run, and the best TSLM comes within $gap_lo–$gap_hi AUROC of the best baseline, though every TSLM stays below the baseline with the same inputs. Replayed as a live monitor on $mon_total unseen runs, the alarms of our full model are right $a_right of the time and fire at a median step of $a_median.

Limitations

  • Classical baselines are strong on this task. With the same inputs, the classical baselines still score above each TSLM. $label_a comes closest: within $gap_lo–$gap_hi AUROC at $early steps, a gap that is not statistically significant.
  • How much $label_a uses the ECG is untested. We did not run a test that shuffles its series between runs, so we do not claim $label_a relies on the ECG. $label_c, which reads only the ECG, scores above chance.

The Agent ECG

Our TimeNet connector for nebius/SWE-agent-trajectories (TimeNet PR #832) splits every run into checkpoints: the first $k_first, 10, 15, 20 or $k_last steps of a run that is still going. A checkpoint never contains the end of the run, so no input gives the outcome away. We call the 19 series recorded at every step the agent's ECG: like a heart ECG, a few lines over time that a trained reader scans for warning signs. It is a multichannel event trace, not a waveform:

4 lengths

the agent's thought, its command, the environment's reply, and the whole conversation so far

5 actions

edit, create a file, run code, read, search

5 replies

rejected edit, traceback, command error, timeout, silent success

5 patterns

repeated command, same file as the last edit, and whether an edit touches a source, test or own file

The data is split by repository, so no repository or issue appears in two splits. Most runs fail, and the longer a run goes on, the more likely it is to fail:

Model

OpenTSLM (Langer et al., 2025) extends pretrained language models to read time series as a native input. We use its SoftPrompt variant, which the paper recommends for short series: a small encoder turns each of our 19 series into tokens that sit in the prompt next to the text, and only the encoder, a projection layer and LoRA adapters are trained (about 14 M parameters). We start from the released Llama 3.2 1B checkpoint at the end of the paper's training curriculum ($base).

We train three models on nested inputs: $label_c reads only the 19 series, $label_b adds the agent's thoughts, and $label_a adds the issue and learns two more tasks, how the run will end and a short status report.

As a Live Monitor

A monitor sits on top of a model and turns its prediction at every step into something an operator can act on: a health score from 0 to 100 that compares the run with runs of the same age, a state (stable, watch, low, critical), and an alarm after $hold critical steps in a row. We replayed $mon_total unseen test runs step by step through two monitors: one on $mon_name, and one on the signals baseline. The runs were all $mon_resolved resolved test runs with at least 20 steps, plus $mon_failing random failing ones; neither monitor chose them.

The two monitors flag mostly different runs: $a_only only by $mon_name, $s_only only by the signals baseline, and $both by both. Part of $mon_name's head start comes from the issue text: half of its alarms fire at the earliest possible step, and they cluster by issue. $mon_name's Other Two Tasks

Besides pass or fail, $mon_name learns to predict how a run will end (one of six endings) and to write a short status report whose last sentence forecasts the rest of the run. Scores on $task_scope, pooled over checkpoints:

The majority baseline always predicts the most common ending, the median remaining steps, and "will not resolve".

$mon_name is about level with the signals baseline on the ending and writes reports in the right format almost every time. Its forecast is weaker: its remaining-steps error and its pass/fail call in the report both trail the signals baseline.

A Second Round

Checks on validation pointed to two fixes, and we retrained one model for each, with the rule for success fixed before training. $label_c2 adds three count channels to the 19 series: steps since the last success, tracebacks so far and code runs so far. $label_a2 trains $label_a against overfitting (one epoch, the natural share of successes, LoRA dropout, finer early stopping) and keeps the first thoughts of long runs as well as the latest. Training

Each model was fine-tuned on one $gpu. Training took $h_c h ($label_c), $h_b h ($label_b) and $h_a h ($label_a), $gpu_hours GPU-hours in all. OpenTSLM's eager attention ran out of memory on $label_a's long prompts; switching to PyTorch SDPA (the same math) made it fit and cut its training time by more than half. The second round ran on one $r2_gpu each: $h_c2 h ($label_c2) and $h_a2 h ($label_a2).
